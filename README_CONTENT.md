# Управление контентом лендинга франшизы Dомиан

Сайт работает как статическая страница GitHub Pages без сборки. Публичные показатели, рейтинги, CTA, контакты и путь к PDF находятся в `assets/js/content.js`. Структура страницы — в `index.html`, оформление — в `assets/css/styles.css`, динамические блоки и взаимодействия — в `assets/js/app.js`.

## Важное правило обезличивания

Финансовые рейтинги и многоофисные кейсы намеренно обезличены.

> Не добавлять реальные названия офисов и собственников в публичные финансовые рейтинги без отдельного согласования.

Также нельзя добавлять в рейтинги и кейсы города, адреса, фамилии, внутренние идентификаторы, скрытые подписи, `data-*`, `title`, `aria-label`, комментарии или иные данные, по которым можно определить конкретного франчайзи. Общая география сети в `cities` и на карте может оставаться: она не связывается с финансовыми результатами.

## Масштаб сети: 70+ и другие показатели

Объект `network` хранит основные показатели:

```js
network: {
  officesDisplay: "70+",
  since: "2008",
  rostovAddressesDisplay: "40+",
  developerChannelsDisplay: "90+"
}
```

Карточки первого экрана меняются в `heroMetrics`, блок масштаба — в `networkMetrics`. При обновлении публичной цифры синхронно проверьте оба массива и объект `network`.

## Финансовые рейтинги

Рейтинги находятся в `performance`:

- `h1_2026` — I полугодие 2026;
- `year_2025` — 2025 год.

Для каждой строки разрешены только:

```js
{ rank: 1, value: 44408712.04, display: "44,4 млн ₽" }
```

Не добавляйте поля `office`, `city`, `owner`, `name` или аналогичные. `value` используется для длины визуальной полосы, `display` — для публичного отображения. Во всех текстах результат должен называться комиссионным оборотом, а не прибылью или доходом собственника.

## Многоофисные кейсы

Два обезличенных примера находятся в `multiOfficeCases`. Здесь меняются:

- количество офисов;
- совокупный комиссионный оборот за 2025 год;
- совокупный комиссионный оборот за I полугодие 2026;
- публичный обезличенный headline.

Не указывайте названия офисов, города и данные собственников.

## Партнёрские услуги: 40 / 30 / 30

Схема распределения задаётся в одном месте:

```js
partnerServicesSplit: {
  agent: 40,
  owner: 30,
  centralOffice: 30
}
```

Публичный смысл схемы: 40% агенту, 30% собственнику франшизного офиса, 30% центральному офису; 70% остаётся в офисе и его команде.

## PDF-коммерческое предложение

Утверждённый PDF подключается полем:

```js
proposalPdf: "assets/docs/domian-franchise-proposal.pdf"
```

Сам файл должен лежать по адресу `assets/docs/domian-franchise-proposal.pdf`. Не редактируйте, не конвертируйте и не пересобирайте его в рамках работы над сайтом. Если поле пустое или путь некорректен, все PDF-кнопки автоматически скрываются, поэтому битой ссылки на сайте не будет.

## CTA

Тексты основных действий меняются в объекте `cta`:

```js
cta: {
  primary: "Получить персональный расчёт",
  city: "Рассчитать запуск в моём городе",
  consultation: "Обсудить открытие офиса",
  pdf: "Скачать подробное КП"
}
```

Основные CTA ведут к финальному контактному блоку. Не добавляйте публичный калькулятор прибыли без утверждённой формулы.

## Контакты и форма

Контакты задаются в `contacts`:

```js
contacts: {
  phone: "+7 (863) 300-00-04",
  email: "",
  telegram: "",
  whatsapp: "",
  formEndpoint: ""
}
```

Пустой канал не показывается. Форма создаётся только при корректном HTTPS-адресе `formEndpoint`. Если endpoint не задан, сайт не имитирует успешную отправку и показывает только реальные настроенные способы связи.

## Условия и запуск

- `conditions` — карточки роялти, рекламного сбора, договора, помещения и срока запуска;
- `launchSteps` — пять этапов открытия офиса;
- `cities` — общая география присутствия, не связанная с финансовыми рейтингами.

## Публикация и проверка

Разместите содержимое корня проекта в основной ветке GitHub Pages. Перед публикацией проверьте:

- первый экран и навигацию;
- обе вкладки рейтинга мышью и клавиатурой;
- мобильное меню и sticky CTA;
- многоофисные кейсы;
- схему 40 / 30 / 30;
- условия, FAQ и финальный контакт;
- скачивание PDF;
- отсутствие горизонтального переполнения и ошибок консоли;
- отсутствие идентифицирующих данных в финансовых блоках и клиентском JavaScript.

## Новая версия (ветка redesign/blueprint): что добавлено в content.js

Визуальная система «чертёж → здание → сеть». Все тексты и данные по-прежнему в `assets/js/content.js`. Пустые поля на сайте не показываются — заглушек на живой странице нет.

- `asOf` — дата актуальности публичных цифр сети. Если заполнена, попадает в сноску к «70+ офисов».
- `heroFacts`, `networkMetrics` — цифры первого экрана и блока «Сеть»; поле `note` привязывает сноску из `notes`.
- `contours`, `modules` — восемь модулей системы в трёх контурах (порядок = порядок сборки схемы). У модуля: `action`, `notBuild`, `inside`, `artifact`.
  - `artifact: { src, alt, caption }` — реальный обезличенный артефакт (скрин Domianix, программа обучения, фото). Пока `null`, блок «Доказательство» не выводится. Интерфейсы и функции не придумывать.
- `performanceSampleSize` — сколько франшизных офисов в рейтинге; если заполнено, добавляется в сноску.
- `partnerServices` — категории партнёрских услуг. Распределение 40 / 30 / 30: собственнику офиса — 30%. Формулировку «70% остаётся в офисе» не использовать.
- `conditions`, `priceNote`, `requirements`, `afterRequest` — условия, объяснение, почему нет цены входа, требования к партнёру, шаги после заявки. Стоимость входа не публикуется нигде.
- `team` — люди франшизного направления `{ name, role, stage, photo, contact }`, только с согласия.
- `stories` — истории собственников `{ name, city, since, path, quote, photo }`, только с письменного согласия и без финансовых цифр. Секция появляется автоматически.
- `trust.rgr.certificate`, `trust.rgr.url` — номер и ссылка на сертификат РГР; `trust.trademark` — номер товарного знака.
- `notes` — тексты сносок. Нумеруются автоматически в порядке появления на странице.
